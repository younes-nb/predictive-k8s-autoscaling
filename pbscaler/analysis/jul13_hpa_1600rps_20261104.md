## 6. Comparison: HPA ON vs Fixed Fleet (Max 8)

| Configuration | Behavior at 1600 rps |
|---------------|----------------------|
| Fixed 8 (no HPA) | Not measured at 1600 (cliff at 1025–1100 rps, latency cliff) |
| HPA ON (max=8) | Sustains 1600 rps: 0 interrupted iterations, success ≥ 0.9745, but **98.2% of 5s windows violate the 200 ms SLO** |

### Key Insight

HPA ON keeps the service fleet **structurally stable** at 1600 rps (no crashes, no dropped requests), but the 200 ms SLO is violated ~98% of the time (median front P90 = 531.7 ms).

**Verified jul13-series operating points (complete 4h15m files):**

| RPS (HPA ON, max=8) | Violations (P90>200ms) | front_p90 median |
|---------------------|------------------------|------------------|
| 1000 | 0.0% (3060/3060 ok) | 10.4 ms |
| 1500 | 61.4% | 239.2 ms |
| 1600 | **98.2%** | 531.7 ms |

**Violation drift caveat:** at 1500 rps the violation rate *drifts upward* through the run (per-30-min windows: 22% → 30% → 38% → 45% → 56% → 84% → 98% → 100%), as backlogs accumulate under a capped fleet (HPA max=8). A first-12-minute snapshot of that same run showed only 16.4% — which is how the earlier "8.6% / 1500 rps" claim arose (12-min partial files of related runs showed 7.9–16%). **Short snapshots under-report violations; only complete-run files are valid.**

## 9. PBScaler RF Model — and why 100% "accuracy" is not a real result

Trained on this dataset (`simulation/RandomForestClassify.py` style encoding: per-service [index, qps, count]):

| Metric | Value |
|--------|-------|
| Samples | 3,060 (all labeled: 3005 violation / 55 ok) |
| Services | 43 |
| **Train accuracy** | 1.0000 (**meaningless — scored on the training set**) |
| Stratified 80/20 test accuracy | 98.4% (= majority-class rate) |
| Stratified test AUC | 0.545 |
| Stratified recall on "SLO ok" | 9.1% |
| Temporal 70/30 test AUC | 0.500 (coin flip) |
| Temporal recall on "SLO ok" | **0%** — never predicts "ok" on unseen data |

### Why it looked perfect — three compounding causes

1. **Evaluated on the training set.** An unpruned RandomForest (default depth/leaf settings) shatters any finite training set; all 3060 feature rows are unique (the per-service index alone guarantees uniqueness), so the forest memorizes them exactly. `model.score(X_train, y_train) = 1.0` is a property of the estimator, not of the data.
2. **Extreme class imbalance.** At flat 1600 rps the system violates the 200 ms SLO 98.2% of the time, so "predict violation always" achieves ~98% accuracy with zero discriminative power.
3. **Labels are degenerate at a single operating point.** The 55 "ok" samples are borderline noise dips (front P90 156–200 ms); their total_qps is actually *higher* than violation samples (13,041 vs 11,609 — during violations service QPS collapses from errors), so the apparent signal direction is backwards noise. No set of features selects these 55 rows from the other 3005.

**Bottom line:** as an SLO-violation *predictor* on unseen data this model is a constant "violation" classifier (AUC ≈ 0.5–0.55). For PBScaler at this load it is behaviorally harmless — "always scale up" is the correct policy at 1600 rps — but it learns no service-level discrimination. For a genuinely discriminative model, training data must mix operating points (e.g., 500 / 1000 / 1500 / 1600+ rps) so both classes have support, and evaluation must be a hold-out split reporting per-class recall and AUC.

## 10. Threats to Validity

1. **Single run** — no replication at 1600 rps.
2. **Sequential tests** — earlier ladder runs may have warmed caches/pools.
3. **Preserve services** — 100% 500s is app bug, not capacity issue.
4. **Open-loop only** — closed-loop behavior may differ (retry amplification).
5. **Single cluster state** — no concurrent control-plane load.

---

## 11. Conclusion

**At flat 1600 rps with HPA ON (max replicas=8), the cluster is structurally stable (15.4M iterations, 0 interrupted, success ≥ 0.9745, 0 restarts) but violates the 200 ms SLO in 98.2% of 5s windows (median front P90 = 531.7 ms).**

- 1600 rps exceeds the HPA-on comfortable operating point: the SLO is violated essentially the entire run.
- The companion RF model is a degenerate "always violation" classifier on this data (§9) — behaviorally fine for PBScaler at this load, but not a discriminative SLO predictor.
- Earlier ladder/HPA percentages (e.g., "1500 rps → 8.6%") came from 12-minute partial-file analyses; the complete 1500-rps file measures 61.4% (see §6 verifier table).
