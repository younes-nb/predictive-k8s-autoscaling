## 4. Key Findings

### 1. **k6 Saturation on 14-July**
The 14-July run showed clear signs of **load generator saturation**:
- VUs dropped from 1200 to ~600 in the last hour
- k6 could not maintain 1600 rps delivery
- 673 interrupted iterations (vs 0 on 13-July)
- Total iterations: 6.1M vs 15.4M (−60%)

This indicates the **load generator itself became the bottleneck** on 14-July, not the cluster.

### 2. HPA Behavior
Both days: HPA was ON with `maxReplicas=8`, all services scaled to 8/8 replicas.
- 13-July: HPA had 4+ hours to stabilize before peak
- 14-July: Same HPA state, but load generator failed first

### 3. Cluster Capacity
- Both days: **0 pod restarts, 0 OOMKilled, 0 Evicted**
- Cluster absorbed 1600 rps on 13-July without service failures
- 14-July failure was load-generator side, not cluster

---

## 5. Root Cause: Load Generator Bottleneck

The 14-July failure was **not a cluster capacity issue** — it was the **load generator (k6) saturating**:

- 1600 rps × 1200 VUs = sustained high connection count
- k6 on loadgen (10.10.1.1) exhausted file descriptors / CPU / network
- VUs dropped from 1200 → ~600 in final hour
- Connection timeouts in k6 logs: "request timeout" to gateway

**Recommendation for future runs:**
- Use multiple load generators at >1600 rps
- Increase loadgen resources (ulimit, CPU, network)
- Monitor k6 VU utilization; cap RPS at ~90% of VU capacity

## 5. Conclusion

| Metric | 13-July | 14-July | Verdict |
|--------|---------|---------|---------|
| **1600 rps sustainable?** | ✅ Yes (15.4M iter) | ❌ No (6.1M iter, k6 saturated) | — |

**Conclusion:** The cluster **can handle 1600 rps with HPA ON (max 8 replicas)** as proven on 13-July. The 14-July run failed due to **load generator saturation**, not cluster capacity. The 13-July results are the valid measurement for 1600 rps HPA ON capacity.
