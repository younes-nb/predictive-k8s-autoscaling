## WHAT THIS REPO IS

Research benchmark on Kubernetes (TrainTicket microservices): predictive (CPA)
autoscaling vs the vendored PBScaler baseline vs stock HPA. Four parts with
**separate, incompatible dependency sets**:

- Root ML pipeline (`preprocessing/` → `pipelines/` → `training/` → `core/`, plus
  `analytics/`, `tooling/`, `shared/`, `madu/`): trains per-microservice
  CPU/mem forecasters on the **Alibaba 2022 microservice traces**.
- `madu/`: SoCC'22 Madu workload-predictor reimplementation.
- `pbscaler/`: vendored PBScaler controller, cluster-adapted. `pbscaler/README.md`
  is the authoritative record of cluster facts, SLO-label semantics, and
  documented upstream deviations — read it before touching that tree.
- `deploy/`: CPA (CustomPodAutoscaler) per-deployment pods + image build.
- `benchmark/`: HPA 25k/4h rerun tooling (`failure_recorder.py`,
   `run_experiment.sh`, `monitor_v2.py`, `log_streamer.sh`,
  `summarize_failures.py`, `analyze_delivery.py`, `backfill_pod_state.py`,
  `dump_mimir.sh`, `dump_loki.sh`, `rotate_run_logs.sh`, tunnel helpers).

There is **no test suite, linter, or CI** — verification means short real runs.

### What is recorded

5 s resolution. Pod/container level: CPU, CFS throttling, working set / RSS /
cache / limit, OOM events, per-pod network rx/tx, fs reads/writes, blkio,
processes. kube-state-metrics: requests/limits, readiness, restarts, HPA
current/desired/max. node_exporter: node CPU/mem/net/disk/fs. Istio: requests,
latency histograms, TCP.

**Not recorded: JVM/heap/GC.** `jvm_*`, `tomcat_*`, `http_server_requests_*` are
all empty. The dominant failure family (`ts-user-service` / `ts-auth-service`
exhausting their `-Xmx512m` heap) is therefore only visible indirectly — container
working set vs the 1 Gi limit, restarts, and app logs. Enabling Beyla gives
per-service RED metrics but **not** heap.

Retention: **1440 h (60 days)** on Mimir and Loki.

## THE BENCHMARK

### One orchestrator

```bash
run_experiment.sh --day <NASA day> --duration <minutes> --max-requests <peak/min> \
  --local [--ssh] [--shape hpa|pbscaler] [--name ...] [--dry] [--trace-only]
```

It takes the trace **day** and the measured **duration**, selects the
**highest-standard-deviation** window of that day of that length from the real
NASA-HTTP archive (`benchmark/nasa_trace_slice.py`), writes the slice to
`RUN_DIR/trace_slice.csv`, and records its sha256 in `params.json`.

**k6 runs from the repo**: `load_testing/k6/trainticket.js` (generator),
`load_testing/k6/launch_k6.sh` (wrapper), `load_testing/seeds/tt_users.json`
(seeds). Nothing is copied to a fixed `/opt/loadgen` path any more; `LOADGEN_HOME`
only holds run outputs. Override with `GENERATOR_JS`, `LAUNCH_K6_SH`,
`SEED_FILE_LOADGEN`, `K6_BIN`, `K6_OUT_DIR`.

### SLO definition

Front (gateway → `ts-ui-dashboard`) **p90 > 200 ms** on a 5 s tick:
`histogram_quantile(0.90, sum(rate(istio_request_duration_milliseconds_bucket{...}[1m])) by (le))`.
The dataset labels each tick `slo_reward` (1 = ok, 0 = violation, −1 = no data);
the violation rate is `count(0) / (count(0)+count(1))`. Anything else ("5xx rate",
"p95") is a different metric and is not comparable.

### Calibrating MAX_REQUESTS (do this on the new cluster)

There is **no usable calibration yet**. Every measurement so far came from the old
8-core cluster and is not transferable: the same `MAX_REQUESTS` produced wildly
different violation rates there depending on whether the masters were schedulable,
tainted, quota-capped or sharing their memory with monitoring. Those numbers were
deleted rather than carried forward as false anchors.

Target for step 1: **10–20 % SLO violations** (front p90 > 200 ms per 5 s tick).
`MAX_REQUESTS` is the knob, and it must be calibrated on *this* cluster:

1. Run step 1 at a moderate starting load (a few hundred to a few thousand
   iterations/minute is a safe place to begin on a cluster this size) and treat
   the result purely as a first data point.
2. Measure the violation rate from the dataset's `slo_reward` column.
3. Move `MAX_REQUESTS` and rerun until it lands in 10–20 %.
4. Record the resulting pair in this file — that becomes the first real anchor.

Note that the response is **not** a smooth gradient: violations arrive in
multi-minute episodes driven by cold start and recovery dynamics, so two runs at
the same setting can differ a lot. Prefer re-running over fine interpolation.

Takeaway: 30 000 is **under target** on a clean run. The 8-core-era numbers do
not transfer, and the two 30 k runs bracket the 10–20 % band, so the usable
signal is "30 k is too low on this cluster" rather than a local gradient.

**The response is flat from 30 k to 120 k (3.2 / 2.8 / 2.8 %).** 34 M requests at
2363 req/s still leaves the front p95 at 37 ms, so `MAX_REQUESTS` is not the
binding constraint in this range — the new cluster is roughly an order of
magnitude larger than the old 8-core one, and the front end is nowhere near
saturation. Calibration therefore has to move by a large factor, not by ±20 %.

Per-pod limits, not host capacity, are what saturates first (60 k window):
`ts-auth-service` sits at 100 % of its 2-core limit and ~148 % of its 1 GiB
limit; `ts-route-service` / `ts-train-service` throttle 85–99 % of CFS periods.
Nodes stayed at ~19 % CPU / ~4 % memory.

Caution when reading `kube_*` metrics: **two kube-state-metrics replicas are
scraped, so every kube-state series is duplicated.** `sum by (pod)` doubles
limits/requests; use `max by (pod)`. cAdvisor series are not duplicated.

## LOAD GENERATOR KNOBS (2026-11-19)

All optional, all set in the environment; the defaults below are what a plain
`run_experiment.sh` invocation now uses.

- `VUS_MODE=auto|static` (default `auto`). Auto derives the VU cap from the
  offered load instead of from the seed count:
  `ceil(MAX_REQUESTS / 60 * VUS_D_MAX * VUS_SAFETY)`, `VUS_D_MAX=0.5`,
  `VUS_SAFETY=2`. A pool pinned to 2999 was simultaneously ~30x oversized at low
  load (120k used 7-94 active VUs) and the binding constraint at high load
  (480k pinned 2999 and still dropped 63% of iterations). `static` restores
  `PRE_ALLOCATED_VUS = MAX_VUS = SEED_POOL`.
- `TRACE_SELECT=transitions|std|tv` (default `transitions`). Window objective for
  `nasa_trace_slice.py`. `transitions` maximises direction changes in the
  per-minute rate and is **scale-invariant**; `std` is the original
  highest-standard-deviation rule; `tv` maximises total variation and is
  load-dependent. Measured on 13-Jul/240m: transitions picks 11:17Z
  (168 turns, mean/peak 0.456), std picks 10:00Z (163 turns, 0.373) -- the
  transition window carries **+22% mean load** at the same `MAX_REQUESTS`.
- `LOGIN_START_JITTER_S=900`. Spreads each VU's first login over that many
  seconds (deterministic per `__VU`), so 2999 VUs no longer stampede
  `ts-auth-service` at t=0. `0` restores the old herd.
- `LOGIN_BACKOFF_JITTER=0.5`. +/- fraction on the login backoff, so retry waves
  stop re-synchronising. `0` = deterministic.
- `ALLOW_SEED_REUSE=1`. Permits `MAX_VUS > USER_POOL` (accounts shared). Without
  it the orchestrator **fails closed** when the seed pool is too small, naming the
  number of accounts needed. The VU cap is never silently clamped: a clamp would
  make the generator the bottleneck instead of the cluster. The seed pool is
  grown with `load_testing/seed_tt_users.py` (or the parallel
  `/tmp/opencode/seed_parallel.py` used on 2026-11-20 to reach 12 000 accounts).

See `reports/stage7_28/exp13jul/slo_metric_blindness_20261119.md` for why the
SLO number alone must not be used to calibrate.

- Every PBScaler knob is a `PBS_*` env var (`pbscaler/config/Config.py`) — never
  edit configs for a run.
- Root pipeline defaults: `shared/config_paths.py`,
  `shared/config_preprocessing_defaults.py`, `shared/config_training_defaults.py`,
  re-exported via `config/defaults.py`.
- `shared/features.py` (`FEATURE_SETS`) is the single source of truth for
  table/feature/target definitions.
- Dataset roots are env-overridable: `DATASET_ROOT` (default `/dataset`, which
  does **not** exist on these nodes), `PARQUET_ROOT`, `WINDOWS_DIR`, `RAW_ROOT`,
  `MODELS_DIR`, `LOGS_DIR`.
- Interpreter: `pbscaler/.venv` (Python 3.10.12) for pbscaler; the old
  micromamba `venv` at `/users/younes02/mamba/envs/venv` **does not exist** any
  more.

## PERMANENT FIXES (carry these forward)

1. **Readiness probe** on `ts-ui-dashboard` (Ansible task).
2. **Mongo stale connection** — DestinationRule `mongo-idle-timeout`
   (`roles/cluster_addons/tasks/train_ticket.yaml`). `idleTimeout: 0s` alone is
   **not enough** (2026-11-20): with an idle namespace the driver still held a
   dead pooled connection and the first request after a cold reset returned 500
   `Prematurely reached end of stream`. The rule now also sets
   `maxConnectionDuration: 30m` (recycle before conntrack/node/sidecar events can
   reap a connection) and `tcpKeepalive` (30s/10s/3), so Envoy detects a silently
   dead upstream in ~60 s instead of hanging. `run_experiment.sh` phase 0b now
   probes the mongo path (a bogus login, which is HTTP 200 by design) up to 12
   times and **refuses to start** if it fails, so a stale pool can never be
   mistaken for a load condition.
3. **JWT renewal** in the generator: unconditional `ensureLogin(ST)` per iteration,
   45-min refresh, admin login cooldown.
4. **`failure_recorder.py`**: `svc_pods_regex()` uses `_re2_escape` (RE2 rejects
  `\-`); `q()` logs failures; `sys` is imported (a missing `sys` import used to
  kill the recorder on the first failed Mimir query); sidecar lines captured.
5. **`log_streamer.sh`**: one `kubectl logs -f --all-containers` per **pod** (Istio
  1.30 runs `istio-proxy` as a native sidecar in `spec.initContainers`), session-id
  cleanup, `timeout --foreground`.
6. **Orchestrator hardening**: stale-collector reaping, disk watchdog, log
  rotation (`rotate_run_logs.sh`), SIGINT-safe PBScaler, `run_status.json`,
  archive manifest + gzip verification.
7. **`dump_loki.sh`**: recursive sub-second splitting so chunks never hit
  Loki's 4 900-line page cap; gzips every chunk.
8. **`tunnel_lib.sh`**: every port-forward clears a stale holder, health-checks
  `/ready`, and retries. `kube_tunnel.sh` fails over across masters.
9. **Masters untainted + kubelet reservations** (`roles/cluster_addons/tasks/kubelet_reservations.yaml`,
  now declarative) instead of a taint, which made pods unschedulable.
  kubeReserved 1 C/1.5 Gi + systemReserved 0.5 C/1 Gi on every node, so
  allocatable is 6.5 C / 9.2 Gi on the 8 C / 11.7 Gi nodes. Verified applied.
10. **Monitoring out of the cluster** on its own host; Alloy stays in-cluster.
11. **No Prometheus.** Alloy is the scraper.
12. **k6 runs from the repo**, not from a copied fixed path.
13. **Loki `reject_old_samples_max_age: 9999h`** — the 7-day default rejected
    every batch from long-lived pods, and `0` is NOT "disabled" in Loki 3.x: it
    means "reject anything older than now", which dropped 100 % of batches.
14. **Tempo data at `/var/tempo`**, not `/tempo` (that path is the binary).
15. **Image UIDs**: mimir 0, loki/tempo 10001, grafana 472 — data dirs are chowned
    to match.
16. **ResourceQuota is declarative** (`roles/cluster_addons/tasks/resource_quota.yaml`,
  `tq_*` vars) — it was live-only, so a fresh cluster had no namespace ceiling.
  Requests only, no `limits.*` caps: a limits cap deadlocks HPA scale-out.
17. **Tempo runs on the monitoring host, not in-cluster** (2026-11-19). The
  `cluster_addons` tempo task deployed a Tempo with a `local-path` PVC, i.e.
  node-local storage: 43 GB of trace blocks landed on **worker1** and pushed it
  to 84 %, where the kubelet evicted benchmark pods mid-run (that is what made
  the 480 k probe's final cold reset fail). Now
  `roles/monitoring/templates/docker-compose.yml.j2` publishes **4317/4318**,
  `roles/cluster_addons/templates/alloy.yaml.j2` and the `otel-tempo` provider in
  `tasks/istio.yaml` point at `<monitoring_host>:4317`, and `tasks/tempo.yaml`
  applies only the Istio `Telemetry` sampler.
18. **Alloy's positions/WAL are persisted** (`alloy-data` PVC, 5 GiB, in
  `templates/alloy.yaml.j2`). Without it every Alloy restart replayed every
  pod's log from the beginning and Loki rejected the backlog as "entry too far
  behind" — one restart cost a ~3 h log gap.

  Services (`tasks/monitoring.yaml`, `tasks/grafana_datasources.yaml`): Mimir,

  Grafana with three dead datasources.

## GOTCHAS

- **Never edit a bash script while it is running.** `run_experiment.sh` reads
  itself incrementally; an edit shifts byte offsets and the next read lands
  mid-line (this once killed a 4 h run before its post-processing).
- **`pkill -f <pattern>` can match your own command line.** Use the bracket trick
  (`pkill -f 'log_[s]treamer.sh'`) or you kill your own shell.
- **Mimir bucket series expire** — query promptly after a run.
- **Loki caps a query at 5 000 entries**; chunk accordingly.
- **`master1` can hang while the cluster keeps serving.** `kube_tunnel.sh` fails
  over; a dead ssh holding 127.0.0.1:16443 otherwise silently kills kubectl and
  every port-forward.
- **`kubectl` and the tunnels do not survive a reboot.** Restart the apiserver
  tunnel explicitly.
- **The ResourceQuota blocks on `limits.*` if you set them** — it deadlocks HPA
  scale-out and leaves deployments with zero pods. The namespace quota caps
  `requests.*` and `pods`; the kubelet reservations are the control-plane
  guarantee.
- **A stale `kubectl port-forward` keeps the port bound** after its pod restarts,
  so the replacement dies with "address already in use" and the service silently
  reads a dead socket.
- **`node_exporter` metrics are NOT cluster-wide.** Alloy runs as a single
  Deployment and its `prometheus.exporter.unix` scrapes *its own* host (master1),
  so `node_cpu_seconds_total` / `node_filesystem_*` describe one node only.
  For cluster-wide node capacity use cAdvisor or `kube_node_status_*`; for
  per-node CPU use `sum by (node) (rate(container_cpu_usage_seconds_total[5m]))`.
- **A 30-min probe and a 4 h run use different trace windows** (the orchestrator
  picks the highest-standard-deviation window of the requested length), so probe
  violation rates are only an order-of-magnitude guide to the 4 h run.
